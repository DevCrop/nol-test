1단계: 운영에 손대기 전
- 현재 운영 전체 파일+DB+uploads+resource/file+.env+.well-known을 동일 시점으로 백업하고 복원 가능한지 확인.
- 최신 사본으로 Docker/스테이징 리허설. 제공된 과거 파일 snapshot만으로 고객 최신 수정까지 일치한다고 가정하지 말 것.
- 실제 호스팅 PHP/MySQL 버전/확장 및 PATH_INFO 지원 확인.
- 특히 SQL의 utf8mb4_0900_ai_ci는 MySQL 8용. 운영이 5.7/MariaDB이거나 지원 여부 미확인이면 SQL 적용 중지. 승인 SQL을 즉석 치환하지 말고 별도 호환본 검증 필요.
- .env/.sql/로그 외부 접근 차단과 업로드 PHP 실행 금지는 라우팅과 별개. 연결 도메인에 .htaccess가 적용되지 않으면 서버 대체 통제 확인 필요.
- 공개 도메인의 HSTS includeSubDomains/preload 또는 브라우저 HTTPS-only가 있으면 gate HTTP가 브라우저에서 강제 HTTPS로 바뀔 수 있음. DNS나 PHP 코드로 이 브라우저 정책을 우회하지 말 것.

2단계: 설정 준비
- production-http.env.example은 양식이며 완성 .env가 아님. 현재 운영 DB 값/프로젝트 SMTP 비밀값/허용 공인 IP를 채워 별도 비밀 채널로 준비.
- APP_ENV=production
- PUBLIC_HOST=bluesquare.kr (운영이 www 대표 주소면 기존 www 기준을 유지)
- GATE_HOST=gate.bluesquare.kr
- GATE_ROUTE_MODE=php
- GATE_ALLOW_HTTP=true
- GATE_ENFORCE=true
- GATE_ALLOW_IPS=허용 공인 IPv4 또는 CIDR (운영 빈 목록은 차단)
- SESSION_SECURE=true 유지. 정확한 gate HTTP 요청에서만 코드가 Secure 속성을 유예.
- SESSION_DOMAIN은 빈 값(host-only), MFA_ENABLED=true.
- SMTP 발신/계정/앱비밀번호는 고객 운영 설정을 사용. 양식의 빈 값이나 개발 QA DB 값을 운영에 쓰지 말 것.
- 구형 .env.gate는 새 .env와 호스트/모드가 충돌하지 않게 정리. GATE_HTTP_PREVIEW=true를 남기면 로그인/CRUD 미리보기 차단.
- 현재 운영 관리자별 실제 수신 이메일과 최고관리자 권한을 확인. 테스트 계정/수신자를 일괄 등록하지 말 것.

3단계: SQL — 사이트별 독립 DB에서 먼저 실행
- 놀 SQL은 dbusrdaehakro0605 / sitekey NOLTHE용.
- 블루 SQL은 dbusrbluesq0211 / sitekey BLUESQ용.
- 반드시 해당 사이트 SQL을 사용. 서로 혼용 금지. 원본 260918.sql 전체 import 금지.
- DB 사본에서 먼저: preflight.sql → changes.sql → preflight.sql → changes.sql 재실행 → 실제 스키마 및 계정 확인.
- 승인 changes.sql에도 사전 검사가 포함되어 있음. DDL은 자동 커밋이므로 전체 트랜잭션 롤백을 기대하지 말 것.
- SQL 실행 도구가 첫 오류에서 중단하는지 먼저 확인. --force/오류 무시/실패 후 계속 실행 금지.
- phpMyAdmin 등 도구가 첫 오류 중단을 보장하지 않으면 그대로 일괄 import하지 말고 가비아/DB 관리자와 안전한 실행 방법 확정.
- CLI가 있는 검증 환경에서는 전체 프로젝트 루트에 sql/와 deploy/를 갖춘 뒤 다음 명령을 각각 실행하고 성공 여부를 확인:
    php deploy/preflight.php source
    php deploy/preflight.php config
    php deploy/preflight.php compat
    php sql/release.php check
    php sql/release.php up
    php sql/release.php check
    php sql/release.php up
    php deploy/preflight.php schema
  사본에서 반복 적용 검증을 끝낸 뒤 운영은 백업/쓰기 중지 상태에서 동일 SQL 적용. 반복 실행은 안전하지만 매번 필수 변경이 생기는 것은 아님.
- preflight/schema가 HOLD면 중지. check 성공만으로 컬럼이 모두 추가됐다고 판단하지 말 것.
- 기존 활성 관리자가 여러 명이고 role_code가 아직 없으면 초기 최고관리자 지정이 모호해 사전 검사가 중단됨. 고객이 지정한 계정을 확인해 별도 처리한 후 진행.
- MFA 이메일은 스키마 SQL에서 임의 채우지 않음. 비어 있으면 고객 확인 후 정확한 no+uid+sitekey를 함께 조건으로 대상 1계정만 별도 갱신/검증.
- QA DB는 기존 seed 최고관리자 이메일 부재를 HOLD로 탐지했음. 이는 운영 계정 확인 결과가 아니므로 운영 이메일을 별도 확인해야 함.

4단계: 실제 업로드 — 유지보수 시간에 한 사이트씩
1. 공개 폼/게시물/대관/첨부/관리자 등 동적 쓰기를 중지하고 최종 파일+DB 백업.
2. 운영 DB에서 호환/사전 검사 → 승인 changes.sql → 변경 후 schema/관리자 이메일/권한 검사.
3. 웹 ZIP을 로컬에서 풀어 파일 manifest와 비교하고 기존 웹 루트에 경로 유지 업로드.
   FTP 전체 미러링/서버의 없는 파일 삭제 금지. uploads/resource/file/.well-known/운영 .env 보존.
   고객이 사후 수정한 정적 콘텐츠/이미지는 구형 개발본으로 덮어쓰지 말고 snapshot과 먼저 대조.
   의존 클래스·리소스 → bootstrap/인증/컨트롤러 → 공개 index 진입점 순. 부분 업로드 중 트래픽 받지 말 것.
4. 별도로 준비한 운영 .env 적용 및 구형 preview/overlay 충돌 제거. DB/파일 쓰기 경로 권한 확인.
5. 기존 홈페이지 HTTPS/공개 폼, gate HTTP 로그인→MFA→권한/세션→CRUD/업로드/다운로드/삭제/감사 기록 확인.
6. 비로그인·비허용 IP 차단, CSRF, .env/SQL/로그 노출 차단, 업로드 스크립트 실행 금지, Apache/PHP 오류 확인.
7. 이상 없을 때만 쓰기 중지 해제. 첫 사이트 안정 확인 후 다른 사이트 적용.

실패 시
- 쓰기 중지 유지. 에러 난 상태에서 다음 SQL이나 나머지 파일을 무작정 계속 적용하지 말 것.
- 비밀번호 해시 자동 전환 등으로 구형 코드와 DB가 달라질 수 있으므로 파일만 롤백하지 말고 동일 시점 파일+DB+첨부 조합으로 복구.
- 배포 후 신규 데이터가 생겼으면 전체 DB 복원 전에 별도 보존/정합성 조정.
